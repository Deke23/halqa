# Engineering specification

Working product name: **Halqa** (Arabic for "loop"). The name lives in one constant on each side (`APP_NAME`); do not hard-code it elsewhere.

Entry: Future Health Digital Innovation Challenge, Population Health, Challenge 05 "Closing the Screening-to-Care Loop", with Challenge 09 "Sustaining Healthy Behaviors" features as the follow-up stage of the same loop. Team Latitude-IT.

This file is the contract between every workstream. If you need to deviate, write the deviation into `docs/DECISIONS.md` (one line each) instead of silently diverging.

## 1. What we are building

A hypertension follow-up loop. A raised blood pressure found at screening becomes **one case**. The case moves through eight states. At every state there is exactly **one accountable owner** and **one due date**. Overdue, rejected and unowned cases surface in a coordinator queue. Severe readings escalate to same-day clinician review. Only a clinician can close a case, and only with evidence or a recorded decision. After treatment starts, the patient gets one small weekly diet or activity action; a missed week shrinks the plan and never resets or penalises.

Two settings share one engine:

- **Abu Dhabi**: result arrives from an IFHAS screening feed (simulated). Patient uses the web app in Arabic or English. Insurance cover is shown before booking.
- **Yaoundé**: result arrives from a clinic reading. Patient is served by SMS and WhatsApp (simulated in a phone-style thread) in French. A nurse is the coordinator.

## 2. Non-negotiable guardrails

Breaking any of these can cost the entry. Tests must exist for the ones marked (T).

1. **Synthetic data only.** Every person, reading, provider and message in the repo is fictional and generated by our own seeded code. No real names of real patients or clinicians. Real organisation names (IFHAS, Thiqa, Malaffi) appear only as labels of simulated sources and every such screen carries a "Simulated" tag.
2. **Rules decide, AI only drafts wording.** (T) No language model output is ever read by routing, urgency, ownership, SLA or closure logic. The wording module returns text only. The engine must work identically with the wording module disabled.
3. **Clinicians close cases.** (T) The `close` action is rejected for every role except clinician, and rejected without an evidence type plus either an evidence reference or a decision note. No timer, job or rule ever sets a case to CLOSED.
4. **Screening is not diagnosis.** A screening reading never produces the word "hypertension" as a diagnosis in patient-facing text. Wording is "raised reading that needs checking".
5. **BP values come only from a validated cuff or ABPM.** Wearable data is shown as a diary (activity, sleep) and is never used as a blood pressure value.
6. **No penalties.** No streaks, no loss framing, no red failure states in the patient app. A missed week triggers a no-blame check-in that makes the plan smaller.
7. **No individual data to employers or insurers.** The dashboard is aggregate only and suppresses any cell with fewer than 5 people.
8. **Thresholds and service levels are placeholders pending clinician sign-off.** They live in one config file, each with a `basis` field, and the UI and docs label them as such. Do not write that any threshold is clinically validated.
9. **Writing style for all user-facing and documentation text:** plain sentences. No em-dashes, no arrows, no marketing words. Every figure in documentation names its source or is labelled as an assumption.
10. **Nothing from any employer.** No proprietary code, data or assets. Open-source dependencies only, with licences recorded.

## 3. Architecture

One deployable container.

```
Browser (React SPA: patient, coordinator, clinician, dashboard, phone simulator)
        |  JSON over HTTPS, Bearer guest token
FastAPI app
  api/        HTTP routes, role checks, request and response schemas
  engine/     case state machine, SLA and escalation rules, closure gate, lifestyle plan rules   (pure Python, no I/O, takes `now` as an argument)

  demo/       demo clock, seed scenarios, reset
  db/         SQLAlchemy models and session

```

- **Backend:** Python 3.12, FastAPI, SQLAlchemy 2, Pydantic 2, `fhir.resources` (R4B), pytest.
- **Running the backend during development:** in Docker inside WSL, through `dev/run.sh` (see the header of that file). This machine's Windows Application Control policy intermittently blocks compiled Python extensions, so a native Windows venv is a fallback only. The backend reads `SQLITE_PATH` (SQLite file location), `DATABASE_URL` (PostgreSQL when set) and `GUEST_TOKEN_SECRET` from the environment.

- **API prefix:** `/api`. OpenAPI at `/api/openapi.json`. The backend owns exact field names. The frontend generates its types from the OpenAPI file checked in at `docs/openapi.json` (`npx openapi-typescript`).
- **Time:** all engine functions take `now`. The API reads `now` from a `DemoClock` (real time plus an adjustable offset stored in the DB) so a judge can advance time and watch a case go overdue. Timestamps are UTC ISO 8601.

## 4. Domain model

### 4.1 Case states

`state` is the last milestone reached. `next_step` describes the one thing that must happen next, who is accountable for it, and when it is due.

| # | State | Meaning | Next step | Accountable owner role | Default service level |
|---|---|---|---|---|---|
| 1 | `RESULT_ISSUED` | Actionable screening result received | Notify the patient | coordinator | 24 h (2 h if severe) |
| 2 | `NOTIFIED` | Message delivered in the patient's language | Patient acknowledges and passes teach-back | coordinator | 72 h |
| 3 | `ACKNOWLEDGED` | Patient confirmed understanding | Complete confirmation by home BP monitoring (HBPM) or ABPM and clinician review of the result | primary care clinician | 14 days |
| 4 | `CONFIRMED` | Clinician reviewed confirmatory readings: raised BP confirmed | Send referral | primary care clinician | 3 days |
| 5 | `REFERRED` | Referral sent to receiving clinician | Receiving clinician accepts, then appointment is booked | receiving clinician until accepted, then coordinator | 2 days to accept, 5 days to book |
| 6 | `APPOINTMENT_BOOKED` | Appointment exists | Visit happens, outcome recorded | receiving clinician | appointment time plus 24 h |
| 7 | `IN_CARE` | Treatment started or surveillance agreed | Review at 4 weeks; weekly lifestyle action runs here | treating clinician | 28 days |
| 8 | `CLOSED` | Closed by a clinician with evidence or a recorded decision | none | none | none |

Rules:

- A case always has `owner_role` and, where assigned, `owner_user_id`. A case whose `owner_user_id` is null while a human step is due is **unowned** and appears in the queue.
- Referral sub-status: `PENDING`, `ACCEPTED`, `REJECTED`. A rejected referral keeps the case in `CONFIRMED` with `referral_status=REJECTED`, clears `owner_user_id`, records the rejection reason, and puts the case in the rejected queue until a coordinator reassigns or a clinician re-refers.
- Confirmation not raised (for example HBPM average below threshold): the case does not auto-close. It goes to the clinician with a suggested closure evidence type `NOT_CONFIRMED`. The clinician closes it.
- Any state may go to `CLOSED` through the closure gate. Closure evidence types: `BP_CONTROLLED`, `NOT_CONFIRMED`, `CARE_TRANSFERRED`, `PATIENT_DECLINED`, `UNREACHABLE_AFTER_PROTOCOL`, `DECEASED_OR_MOVED`, `OTHER_CLINICAL_DECISION`. Every closure stores: clinician id, time, evidence type, evidence reference (reading id, document label) or decision note (min 10 characters).
- A closed case can be reopened by a clinician with a reason. It returns to the state it held just before closure (stored as `state_before_close`) and the next step gets a fresh due date counted from the reopen time.

Clarifications (added after first review):

- `choose_confirmation` and `add_reading` do not change `state`. `choose_confirmation` records the method and sets the next-step label to "complete home readings" or "attend ABPM" (owner stays primary care clinician, patient is the actor). When the readings are sufficient to evaluate, the next-step label becomes "clinician review of confirmation".
- `review_confirmation` with `CONFIRMED` moves `ACKNOWLEDGED` to `CONFIRMED`. With `NOT_CONFIRMED` the case stays in `ACKNOWLEDGED`, stores `confirmation_outcome=NOT_CONFIRMED`, and the next step becomes "clinician closure decision" owned by the reviewing clinician, due in 3 days.
- Severe cases: the patient notification step has a 2 hour service level. In parallel the engine creates a separate `urgent_review` task owned by the clinician role, due in 4 hours. The case `next_step` continues along the normal pathway. If the `urgent_review` task is not completed by its due time it escalates to the on-call clinician at that moment (level 2 at 1 times the service level). The case shows as urgent until that task is completed by a clinician (action `complete_urgent_review` with a note, clinician only).

### 4.2 Urgency

Config file `backend/app/engine/config.yaml` (single source for thresholds and service levels, each entry has `value`, `unit`, `basis`, `status: placeholder_pending_clinician_signoff`).

- `SEVERE`: systolic at or above 180 or diastolic at or above 110. Creates a same-day clinician review step due in 4 hours, flags the case urgent, places it at the top of the queue, and sends the patient the urgent template with red-flag symptom advice. This is routing, so it is rule-based.
- `RAISED`: systolic 140 to 179 or diastolic 90 to 109. Standard pathway.
- Below that the reading is not actionable and no case opens.
- Red-flag symptom check on the patient result screen (chest pain, shortness of breath, severe headache, vision change, confusion, weakness on one side). Any "yes" shows emergency advice immediately and escalates the case to urgent. Emergency text is region config: UAE shows ambulance 998; Cameroon shows "go to the nearest emergency department" with no number.
- HBPM confirmation threshold: average at or above 135/85 over at least 4 days with at least 2 readings per day, first day discarded. ABPM daytime average at or above 135/85. Both in config, both placeholders pending sign-off.

### 4.3 SLA and escalation

`engine.evaluate(case, now)` is pure and returns flags and escalation events to append:

- `overdue` when `now > next_step.due_at`.
- Escalation level 1 at due time: reminder to the owner. Level 2 at 2 times the service level: case goes to the escalation queue for the coordinator lead. For severe cases level 2 is at 1 times and targets the on-call clinician.
- Unreachable protocol for the patient steps: reminder at 24 h, second channel at 48 h, coordinator phone call task at 72 h. After the protocol is exhausted the case is flagged for a clinician decision. It is never closed automatically.
- Evaluation runs on every clock advance, on every case read, and on a 60 second background tick.

### 4.4 Audit

`CaseEvent` is append-only: id, case_id, at, actor_user_id or `system`, actor_role, type, from_state, to_state, payload JSON, reason. Every transition, message, escalation, owner change, consent change, e-consult and closure writes an event. The case timeline in the UI is this log. No update or delete on this table.

### 4.5 Consent and access

- Consent record per patient: `care_coordination` (required for the loop), `messaging_channel` per channel, `share_with_receiving_provider`, `lifestyle_programme`, `research_aggregate`. Each has granted or withdrawn with timestamps. The patient can view and change them. Withdrawing `share_with_receiving_provider` blocks the refer action with a clear message to the clinician.
- Roles: `patient`, `coordinator`, `clinician`, `analyst`. Patients see only their own case. Coordinators see operational fields and readings. Clinicians see everything on cases in their organisation or referred to them. Analysts see only the aggregate dashboard.
- Every staff read of a case detail writes a `CASE_VIEWED` event.

### 4.6 Lifestyle plan (Challenge 09), runs in IN_CARE

- One action per week from a small catalogue (salt, activity, sleep, home BP check). Three sizes each: `full`, `smaller`, `smallest`.
- Weekly check-in: `done`, `partly`, `missed`, optional barrier from a short list.
- `missed` or two `partly` in a row: next week uses the next smaller size and the patient sees a no-blame message. `done` twice in a row: offer (never force) the larger size. No streak counters. No lapse ever resets history.
- Three consecutive missed check-ins create a coordinator task "offer a call". It is a human task, not a message blast.

## 6. API surface

Auth: `POST /api/auth/guest {persona}` returns `{token, user}`. All other routes need `Authorization: Bearer <token>`. Tokens are signed and stateless.

Core:

- `GET /api/me`
- `GET /api/config` public transparency: thresholds, service levels, closure evidence types, template catalogue, languages. Includes each entry's `basis` and `status`.
- `GET /api/cases?queue=all|urgent|overdue|rejected|unowned|escalated|mine&region=` staff only. Returns summaries sorted urgent first, then most overdue.
- `GET /api/cases/{id}` full detail: patient summary, state, next_step (label key, owner, due_at, overdue, escalation_level), the eight-step progress list with timestamps, readings, referral, appointment, messages, e-consults, lifestyle plan, consent, timeline events, `allowed_actions` for the caller.
- `GET /api/my/case` patient shortcut to their own case detail (patient-safe projection).
- `POST /api/cases/{id}/actions {action, payload}` the only way to change case state. Returns the new case detail. `403` when the role may not perform the action, `409 {code, message}` when the state does not allow it, `422` for bad payload.

Actions (role allowed):

| Action | Role | Payload |
|---|---|---|
| `notify` | coordinator, system | `{template_id, language, channel}` |
| `acknowledge` | patient | `{teach_back_answer, red_flags: [], confidence: 1..5}` wrong answer returns a simpler explanation and does not advance; two wrong answers create a coordinator call task |
| `choose_confirmation` | patient, coordinator | `{method: HBPM or ABPM}` |
| `add_reading` | patient, coordinator, clinician | `{systolic, diastolic, pulse?, taken_at, source: HOME_CUFF or CLINIC or ABPM}` |
| `review_confirmation` | clinician | `{outcome: CONFIRMED or NOT_CONFIRMED, note?}` |
| `refer` | clinician | `{to_user_id or to_service, reason}` |
| `accept_referral` | clinician (receiving) | `{}` |
| `reject_referral` | clinician (receiving) | `{reason}` |
| `assign_owner` | coordinator | `{user_id}` |
| `book_appointment` | patient, coordinator | `{slot_id}` |
| `record_visit` | clinician | `{outcome: TREATMENT_STARTED or SURVEILLANCE, note?}` |
| `plan_checkin` | patient | `{status, barrier?}` |
| `complete_urgent_review` | clinician | `{note}` |
| `escalate` | coordinator, clinician | `{reason}` |
| `close` | clinician | `{evidence_type, evidence_ref?, decision_note?}` |
| `reopen` | clinician | `{reason}` |
| `update_consent` | patient | `{purpose, granted}` |

Other:

- `GET /api/cases/{id}/slots` appointment slots, each with a simulated cover line (`covered`, `copay`, `estimated_price`, `currency`, `label`), always tagged simulated.
- `POST /api/cases/{id}/econsults {to_user_id, question}`, `POST /api/econsults/{id}/reply {answer}`.
- `POST /api/cases/{id}/messages/draft {template_id, language, tone?}` returns `{text, source: TEMPLATE or AI_REWORDED, template_id, template_version, validation}`. `POST /api/cases/{id}/messages/send {draft}` staff must approve an AI re-worded draft before it is sent; the event records the approver.
- `GET /api/my/messages`, `POST /api/my/messages/reply {text}` for the phone thread. Replies are parsed by fixed rules only, never by a model: numbered keywords (for example `1` = understood, `2` = call me) and, during home monitoring, a strict blood pressure pattern `SYS/DIA` (two or three digits, a slash, two or three digits, plausible range 60 to 260 over 30 to 160) that is stored through the same `add_reading` path. Anything else gets a fixed "sorry, please reply with ..." message and, after two unparsed replies, a coordinator call task.

  SMS reply grammar (one table in code, state-driven, no collisions):

  | Where the case is | Accepted replies | Effect |
  |---|---|---|
  | Result sent, not yet read | `1` | Marks the result as read and sends the red-flag question |
  | Red-flag question open | `1` yes, `2` no | Yes: emergency instruction at once, case urgent. Either answer then sends the teach-back question |
  | Teach-back question open | `A`, `B`, `C` (case-insensitive) | Correct: case becomes ACKNOWLEDGED and home monitoring instructions follow. Wrong: simpler explanation and the question again. Second wrong answer: coordinator call task |
  | Home monitoring | `SYS/DIA` | Stored as a reading. Severe value gets the urgent template |
  | Weekly action check-in | the letters the check-in message offers | Recorded as done, partly or missed |
  | Any time | `0` | "Call me": coordinator call task |
  | Any time | STOP (and the French and Arabic words in config) | Withdraws consent for that channel |

  Acknowledgement by SMS therefore always includes a teach-back, the same as in the app. Yes/no questions always use digits, multiple-choice questions always use letters, so a number can never be read as a teach-back answer.
- `GET /api/cases/{id}/fhir` FHIR R4 Bundle: Patient, Observation (BP panel with LOINC 85354-9, components 8480-6 and 8462-4), Task per step (owner, status, restriction period as due date), ServiceRequest (referral), Communication (messages), Appointment, CarePlan (lifestyle), Consent, Provenance for closure. Must validate with `fhir.resources`.
- `POST /api/intake/result` simulated source feed. Accepts a small JSON (patient ref, readings, source system, region). Opens a case when actionable. Used by the "simulate incoming result" button.
- `GET /api/dashboard/live?split=none|language|nationality_group|sex|age_band&region=` measures from cases in the DB.
- `GET /api/dashboard/simulation?split=` baseline versus with-loop results from `sim` (precomputed JSON, section 8).
- `GET /api/demo/clock`, `POST /api/demo/clock/advance {hours}`, `POST /api/demo/reset`.
- `GET /api/health`.

Dashboard measures (both endpoints use the same names):
`time_to_notification_h`, `time_to_acknowledgement_h`, `time_to_confirmation_d`, `time_to_consultation_d`, `time_to_care_d` (medians plus p90), `referral_completion_rate`, `appointment_completion_rate`, `treatment_initiation_rate`, `unresolved_results` (count and rate) with `delay_reasons` breakdown, `teach_back_pass_rate`, `patient_confidence_mean`, `plan_checkin_rate`, `re_engagement_after_lapse_rate`. Each has `n`, and `suppressed: true` when n is under 5.

## 7. Wording module (workstream D)

- `templates/*.yaml`: one file per template id with `version`, `purpose`, `channel_limits`, `required_slots`, and text in `en`, `ar`, `fr`. Template ids at minimum: `result_raised`, `result_severe`, `teach_back_question`, `teach_back_simpler`, `reminder_ack`, `confirmation_hbpm_instructions`, `confirmation_abpm_booking`, `referral_sent`, `referral_accepted`, `appointment_booked`, `appointment_reminder`, `weekly_action`, `no_blame_checkin`, `plan_smaller`, `case_closed_summary`, `urgent_red_flags`, and SMS-length variants for the phone thread (160 characters for French where possible).
- `render(template_id, language, slots)` is deterministic and is the default everywhere.
- `reword(text, language, tone, slots)` is optional. Provider chosen by env: `WORDING_PROVIDER=none|azure_openai|anthropic`. Default `none`. The result is accepted only if the validator passes: every number, date, time, name and phone value from the slots appears unchanged; no new numbers; no diagnosis words from a block list; length within channel limit; language detected matches. Otherwise fall back to the template and report `validation.failed_reason`.
- The engine never imports `wording`. Only the API layer calls it.
- Arabic text must be reviewed for register: Modern Standard Arabic, respectful, no dialect, no assumptions about family or lifestyle. French for Cameroon: simple, formal "vous".

## 8. Synthetic data and simulation (workstream D)

- `sim/cohort.py`: seeded generator of a synthetic screened population for each region (default 5,000 per region) with age band, sex, nationality group (UAE: Emirati, expatriate Arab, South Asian, other; Cameroon: single group), preferred language, insurance type, phone channel, and a screening BP reading drawn from documented distributions. Output is a CSV plus a data card `backend/data/DATA_CARD.md` describing every field and every assumption. No Synthea dependency (Java is not available in the build environment); say so in the data card.
- `sim/pathway.py`: discrete-event simulation of the eight-step pathway for the actionable subset under two arms: `baseline` (result report only, no owner, no reminders) and `with_loop`. Every transition probability and delay distribution is a named parameter in `sim/params.yaml` with `value`, `source` and `kind: published|assumption`. Use the published figures given in section 9 and label everything else as an assumption. Include a one-way sensitivity analysis on the three most influential assumptions.
- Output `backend/data/simulation_results.json` consumed by the dashboard endpoint, including splits and the parameter table so the UI can show "what this is based on".
- Also generate HBPM week series, one ABPM day series and one wearable activity series for the demo personas.
- State clearly in outputs and UI text: these are simulated results on synthetic people. They show what the system measures, not clinical effectiveness.

## 11. Definition of done for the prototype

The demo script runs from a fresh browser with no errors:

1. Patient, Abu Dhabi: sees 152/96 result in Arabic and English, passes teach-back, chooses home monitoring, enters readings, sees confirmation reviewed, referral accepted, books a visit with cover shown, then gets a weekly salt action, misses a week, gets a no-blame check-in and a smaller plan.
